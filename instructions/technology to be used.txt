For the product we described, I would **not** use a single-language/single-framework architecture. The application has four very different workloads: normal SaaS/backend work, AI orchestration, heavy media processing, and browser-based real-time editing. Each should use the technology best suited to it.

My recommended production stack would look like this:

| Layer                  | Primary technologies                         |
| ---------------------- | -------------------------------------------- |
| Web app                | **Next.js + React + TypeScript**             |
| Design system          | Tailwind CSS + Radix/shadcn-style primitives |
| Video/image canvas     | WebGL + WebGPU + Canvas + OffscreenCanvas    |
| Browser video/audio    | **WebCodecs**, Web Audio API, AudioWorklet   |
| Browser workers        | Web Workers + WASM                           |
| Main backend           | **TypeScript + NestJS**                      |
| AI/backend workers     | **Python + FastAPI**                         |
| AI workflows           | **Temporal**                                 |
| Agent orchestration    | Custom orchestrator + optional LangGraph     |
| Main database          | **PostgreSQL**                               |
| Vector/RAG             | **pgvector** initially                       |
| Cache                  | Redis                                        |
| Object storage         | S3-compatible storage                        |
| CDN                    | CloudFront / Cloudflare                      |
| Media processing       | **FFmpeg**                                   |
| GPU processing         | Python + PyTorch + CUDA                      |
| Custom model serving   | vLLM / Triton / diffusers / custom workers   |
| Realtime collaboration | WebSocket + Yjs/CRDT                         |
| Search                 | PostgreSQL first, OpenSearch later           |
| Analytics              | ClickHouse                                   |
| Billing                | Internal usage ledger + Stripe               |
| Observability          | OpenTelemetry + Prometheus/Grafana + Sentry  |
| Containerization       | Docker                                       |
| Orchestration          | Kubernetes once scale requires it            |
| CI/CD                  | GitHub Actions                               |
| IaC                    | Terraform                                    |
| Secrets                | AWS Secrets Manager / Vault / KMS            |

Next.js remains a good fit for the primary web application and its current App Router supports the modern React model. ([Next.js][1])

# 3. Video editor technology

This is probably the technically hardest frontend component.

The editor should use:

```text
React UI
       ↓
Timeline engine
       ↓
Media engine
       ↓
WebCodecs
WebAudio
Canvas/WebGL/WebGPU
       ↓
Proxy video
```

**WebCodecs is particularly important.**

It gives low-level browser access to video/audio frames and hardware-assisted encoding/decoding and is explicitly suitable for browser video/audio editing workloads. ([MDN Web Docs][2])

So instead of:

```text
<video>
```

being your entire editor architecture, you operate on:

```text
EncodedVideoChunk
       ↓
VideoDecoder
       ↓
VideoFrame
       ↓
GPU processing
       ↓
Canvas
```

This timeline becomes the source of truth.

# 13. Temporal is extremely useful here

This isn't a normal CRUD application.

Some jobs can take:

```text
5 sec
30 sec
5 min
20 min
several hours
```

And providers fail.

A generation might involve:

```text
Generate
   ↓
Wait provider
   ↓
Download
   ↓
Transcode
   ↓
Create thumbnails
   ↓
Extract embeddings
   ↓
Moderation
   ↓
Store
   ↓
Meter cost
```

Temporal is designed for durable execution: workflows can resume through crashes, network failures and infrastructure interruptions rather than losing state. ([Temporal Docs][4])

Therefore:

```text
Temporal

GenerationWorkflow
RenderWorkflow
FineTuneWorkflow
IngestWorkflow
DubbingWorkflow
ExportWorkflow
```

# 17. RAG database

Initially don't introduce Pinecone/Weaviate/Qdrant unless necessary.

Use:

```text
PostgreSQL
+
pgvector
```

pgvector provides exact and approximate nearest-neighbor search directly inside Postgres and supports cosine, inner-product and other vector distances. ([GitHub][5])

So:

```sql
assets
documents
chunks
scenes
characters
embeddings
```

can remain closely connected.

The three pieces I would consider **non-negotiable architectural foundations** are:

**1. PostgreSQL + Project Graph**, because everything—stories, shots, assets, models, generations and costs—needs relationships.

**2. Temporal + asynchronous job infrastructure**, because media generation cannot be designed like ordinary HTTP requests. Temporal's durable workflow model is particularly appropriate for jobs that span provider calls and multiple processing stages. ([Temporal Docs][4])

**3. A provider-independent AI Gateway**, because OpenAI, Google, xAI, Runway, Higgsfield, ElevenLabs or today's best video model will not necessarily be tomorrow's best model.

That combination lets us start primarily with external APIs as you wanted, while later replacing high-cost/high-volume operations with our own GPU-hosted models **without rebuilding the application**.
